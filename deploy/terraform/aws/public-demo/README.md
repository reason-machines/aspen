# Aspen's public demo on AWS

This directory is how the public demo of [docs/PLAN.md](../../../../docs/PLAN.md)
(section 6) runs: the `place` canvas, where every brush stroke is a `git
push`, plus Aspen itself, deployed with this repository's own AWS module
([`deploy/terraform/aws`](..)). It is also a worked example of running Aspen
on AWS for real, so it is written for anyone who wants to do the same.

| Directory | What it holds | Applied |
|---|---|---|
| [`account`](account) | Once per AWS account: the monthly and daily budget alarms for the whole account (and a CloudFront one), the Route53 zone for the demo's subdomain, ECR repositories | First |
| [`environment`](environment) | Once per environment, `staging` then `demo`: Aspen at `git.<base>`, CloudFront at `cdn.git.<base>`, `place` at `place.<base>` | Staging, then the demo |
| [`account-budget`](account-budget) | The budget check both roots run: a monthly cost budget over the whole account, at most what the owner approved, with an alert that fires by then | (called by both) |
| [`smoke.sh`](smoke.sh) | Checks a deployed environment from the outside | After every deploy |

Hostnames, with the account's subdomain `aspen.example.com` as the example:

| | Staging | Demo |
|---|---|---|
| `place` page, API and `canvas.git` | `place.staging.aspen.example.com` | `place.aspen.example.com` |
| Live canvas image for embedding (CloudFront, `/api/v1/canvas.svg` only, 2 s cache) | `live.place.staging.aspen.example.com` | `live.place.aspen.example.com` |
| Aspen, Git over HTTPS | `git.staging.aspen.example.com` | `git.aspen.example.com` |
| Pack CDN (CloudFront over `/-/express`) | `cdn.git.staging.aspen.example.com` | `cdn.git.aspen.example.com` |
| Git over SSH (off unless `enable_ssh`) | `ssh.git.staging.aspen.example.com` | `ssh.git.aspen.example.com` |

`place` can also sit at the zone's own name: set `place_hostname` to
`base_domain` (Aspen's own demo does this, with the zone
`place.reasonmachines.com`: the page at `place.reasonmachines.com`, Aspen at
`git.place.reasonmachines.com`, staging under
`staging.place.reasonmachines.com`).

## Ground rules

- **A dedicated AWS account, nothing else in it.** Use a member account
  created for the demo (AWS Organizations works well). Never an account that
  runs anything else, and never a production account. Every root sets the
  AWS provider's `allowed_account_ids` to `aws_account_id`, so Terraform
  refuses to run with credentials for any other account.
- **A subdomain of a domain you already own.** Nothing here registers or
  buys a domain. The account stack creates a hosted zone for the subdomain,
  and the owner of the parent domain delegates it with four NS records.
- **Spend the owner approved, watched.** The account stack's budgets have
  no cost filters, so they cover everything in the account, in every region:
  a monthly one, and a daily one that catches a runaway day within about a
  day. They only notify; nothing stops or shrinks anything. The plan was
  $300/month; for the public share the owner approved up to about
  $650/day for a week from 2026-11-06, so the monthly limit is $20,000 and
  the daily one $650 (docs/PLAN.md decisions log). The validation refuses
  more: a larger budget is a reviewed code change. Bring both back down
  when that week is over.
- **Secrets never pass through Terraform state or this repository.** The
  database password, the express signing key and the SSH host key are
  generated by ephemeral resources and written to Secrets Manager with
  write-only attributes (`deploy/scripts/check-terraform-write-only.sh`
  fails CI otherwise). Tokens you create (below) are printed once; keep
  them in your password manager.

## What it costs

Approximate us-east-1 list prices, 730 hours a month, idle. Staging and
the demo differ only in the place task and the database (environment
`main.tf`, `sizing`); the demo is sized for about 500 pushes/s:

| Item | Staging | Demo |
|---|---|---|
| Fargate: Aspen 1 vCPU / 2 GiB | ~$36 | ~$36 |
| Fargate: place, 0.5 vCPU / 1 GiB (staging), 16 vCPU / 64 GiB (demo) | ~$18 | ~$680 |
| ALB (hours and minimal LCUs) | ~$18 | ~$18 |
| Public IPv4 addresses (2 for the ALB, 1 per task) | ~$15 | ~$15 |
| RDS: `db.t4g.micro` with 20 GiB gp3 (staging), `db.m7g.2xlarge` with 400 GiB gp3 at 12,000 IOPS (demo) | ~$14 | ~$540 |
| Secrets Manager, CloudWatch Logs, S3 at rest, CloudFront health probes | ~$3 | ~$3 |
| **Total, idle** | **~$104** | **~$1,290 (about $43/day)** |
| With `enable_ssh` (NLB and its 2 addresses) | +~$24 | +~$24 |

Under load the demo's cost is mostly S3 requests: every push stores three
objects (pack, `.idx` and entry table) at $0.005 per 1,000 PUTs, so 500
pushes/s held for a whole day is about 1,500 PUTs/s, roughly $650/day on its
own, plus ALB capacity units and logs.

Once per account: the hosted zone ($0.50) and ECR storage (cents). Both
environments together idle at about $230, so **run staging only while you
use it**: once the demo is up, destroy staging, or set `place_running =
false` and `aspen_cpu = 512`, `aspen_memory = 1024` there.

Traffic comes on top. CloudFront's first 1 TB out each month is free, then
about $0.085/GB; traffic out of the ALB is about $0.09/GB after the
account's first 100 GB. The `place` swarm is capped server-side (at most
1,000 agents, 120 pushes/s, 20 s per run, 6 starts per hour per address)
and each push is a few hundred bytes, so it is cheap; what can cost money is
people cloning large repositories from Aspen through the CDN, which the
CloudFront budget watches.

## Bring it up

Prerequisites: Terraform 1.11 or newer, the AWS CLI with the Session
Manager plugin (for ECS Exec), Docker with buildx, `git`, `curl`, and
administrator credentials for the dedicated account, for example through
IAM Identity Center:

```bash
aws sso login --profile aspen-demo
export AWS_PROFILE=aspen-demo
aws sts get-caller-identity --query Account --output text   # must print the dedicated account
```

### 1. State bucket

Once per account, in that account (versioned, private):

```bash
aws s3api create-bucket --bucket <state-bucket> --region us-east-1
aws s3api put-bucket-versioning --bucket <state-bucket> --versioning-configuration Status=Enabled
aws s3api put-public-access-block --bucket <state-bucket> --public-access-block-configuration \
  BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true
```

### 2. The account stack

```bash
cd deploy/terraform/aws/public-demo/account
cp backend.hcl.example backend.hcl                 # the state bucket
cp terraform.tfvars.example terraform.tfvars       # account ID, subdomain, alert emails
terraform init -backend-config=backend.hcl
terraform plan -out=account.tfplan
terraform apply account.tfplan
terraform output name_servers
```

AWS emails each alert address once to confirm the SNS subscription; confirm
it, or alerts reach only the direct email recipients of the budget.

Two optional inputs:

- `existing_account_budget_name`: the account already has its budget (an
  organization admin created one with the account). The stack imports that
  budget instead of creating `aspen-account-monthly` and manages it from then
  on, with this stack's limit and alerts; the plan shows it as an import plus
  an in-place update. The budget has `prevent_destroy`: a plan that would
  delete or replace it (renaming it, or naming a different budget) fails.
  Pass the same name to the environments as `account_budget_name`.
- `github_repository`: creates the `aspen-image-publisher` role, which
  `.github/workflows/demo-images.yml` assumes with GitHub's OIDC token
  (only from the refs in `github_image_refs`, `main` by default), so image
  builds need no AWS key (step 4). If the repository uses immutable OIDC
  subjects (`gh api repos/<owner>/<name>/actions/oidc/customization/sub`
  shows `use_immutable_subject: true`), set `github_sub_claim_prefix` to its
  `sub_claim_prefix`, or AssumeRoleWithWebIdentity is refused.

If the hosted zone already exists (created with the account), import it
before the first apply instead of creating a second one:
`terraform import aws_route53_zone.demo <zone id>`.

### 3. Delegate the subdomain

In the parent domain's DNS (wherever `example.com` is hosted), add an `NS`
record for the subdomain (`aspen.example.com`) with the four name servers
from `terraform output name_servers`. Then check:

```bash
dig +short NS aspen.example.com    # the four awsdns name servers
```

Nothing below validates its certificates until this resolves.

### 4. Images

With `github_repository` set in the account stack, run the **Demo images**
workflow from `main` (`gh workflow run demo-images.yml -f
aws_account_id=<id>`): it builds both images from that commit, pushes them,
and prints the `aspen_image` and `place_image` lines in its summary. To build
by hand instead:

ECR tags are immutable, so a tag always names the same image. Build both
images from one commit and push them (the release pipeline's published
images can be copied instead once publishing is turned on):

```bash
registry=$(terraform -chdir=deploy/terraform/aws/public-demo/account output -json ecr_repository_urls)
aspen_repo=$(echo "$registry" | jq -r .aspen)
place_repo=$(echo "$registry" | jq -r '."aspen-place"')
tag=$(git rev-parse --short=12 HEAD)
aws ecr get-login-password | docker login --username AWS --password-stdin "${aspen_repo%%/*}"
docker buildx build -f deploy/docker/Dockerfile --platform linux/amd64 -t "$aspen_repo:$tag" \
  --metadata-file aspen.json --push .
docker buildx build -f deploy/docker/Dockerfile --target place --platform linux/amd64 -t "$place_repo:$tag" \
  --metadata-file place.json --push .
# The values for aspen_image and place_image: the tag plus the digest that
# was pushed. The modules refuse an image pinned by neither a version tag
# (v1.2.3) nor a digest, and a commit tag is neither.
echo "aspen_image = \"$aspen_repo:$tag@$(jq -r '."containerimage.digest"' aspen.json)\""
echo "place_image = \"$place_repo:$tag@$(jq -r '."containerimage.digest"' place.json)\""
```

### 5. Staging

```bash
cd deploy/terraform/aws/public-demo/environment
cp staging.backend.hcl.example staging.backend.hcl
cp staging.tfvars.example staging.tfvars           # account outputs; leave the images unset at first
terraform init -reconfigure -backend-config=staging.backend.hcl
terraform plan -var-file=staging.tfvars -out=staging.tfplan
terraform apply staging.tfplan
curl -fsS "$(terraform output -raw git_url)/healthz"        # the placeholder answers: ok
```

The first apply runs the module's placeholder while the certificates
validate and the database comes up (about 15 minutes, mostly RDS). Then set
`aspen_image` and `place_image` to the two lines step 4 printed in `staging.tfvars`,
plan and apply again. The `place` service starts only after its
`create-database` container has created the `place` role and database.
The plan fails if the account stack's budget (step 2) is missing, above
the approved ceiling (`account-budget`'s `max_limit_usd`), filtered, or has
no alert that fires by that much spend: nothing would be watching spend.

### 6. Operator credentials

Operator commands run inside the tasks with ECS Exec. Each token is printed
once: put it straight into your password manager.

```bash
cluster=$(terraform output -raw ecs_cluster)
aspen_task=$(aws ecs list-tasks --cluster "$cluster" --service-name "$(terraform output -raw aspen_service)" --query 'taskArns[0]' --output text)
place_task=$(aws ecs list-tasks --cluster "$cluster" --service-name "$(terraform output -raw place_service)" --query 'taskArns[0]' --output text)
exec_aspen() { aws ecs execute-command --cluster "$cluster" --task "$aspen_task" --container aspen --interactive --command "$*"; }

exec_aspen aspen repo create smoke/check
exec_aspen aspen token create --subject agent:smoke --grant write:smoke/check   # for smoke.sh

# place's kill-switch operators: an Aspen token with admin on the canvas
aws ecs execute-command --cluster "$cluster" --task "$place_task" --container place --interactive \
  --command "aspen-place operator-token ops@example.com"
```

With SSH on, publish the host key that clients pin:

```bash
key=$(aws ssm get-parameter --name "$(terraform output -raw ssh_host_public_key_parameter)" --query Parameter.Value --output text)
echo "$(terraform output -raw ssh_host) $key" > known_hosts.aspen-staging
```

### 7. Smoke test staging

```bash
ASPEN_URL=$(terraform output -raw git_url) \
SMOKE_REPO=smoke/check ASPEN_TOKEN_FILE=~/.aspen-smoke-token \
CDN_URL=$(terraform output -raw cdn_url) \
PLACE_URL=$(terraform output -raw place_url) \
  ../smoke.sh
```

Every line must say `ok`. Then, by hand:

- **CDN tier.** A clone with `git -c fetch.uriprotocols=https clone` from
  git 2.56 or later reports packfile URIs on `cdn.git.<base>`; older git
  gets `git.<base>/-/express` URIs. Fetch the same pack URL through the
  CDN twice and check the second response has `x-cache: Hit from
  cloudfront`.
- **Past-end ranges on the CDN** (issue
  #45). For a cached
  pack URL of size N, `curl -sI -H "Range: bytes=N-" <url>` shows what
  CloudFront answers past the end. The deployment declares
  `ASPEN_CDN_PAST_END=416`, which is right if it answers `416`; only if it
  answers `206` with an empty body may older clients be sent to the CDN.
  Record the answer in docs/PLAN.md's decisions log.
- **Budget.** `aws budgets describe-budgets --account-id <id>` lists
  `aspen-account-monthly` at `budget_limit_usd`, `aspen-account-daily` at
  `daily_budget_limit_usd` and `aspen-cloudfront-monthly`.
- **SIGTERM.** `aws ecs update-service --cluster "$cluster" --service
  <place service> --force-new-deployment`: the old task's log ends with
  `aspen-place: stopped` before the new task starts, and a tile pushed just
  before is on `main` afterwards.
- **Kill switch.** With the operator token:
  `curl -X POST "$(terraform output -raw place_url)/api/v1/admin/kill-switch" -H "Authorization: Bearer $TOKEN" -H 'Content-Type: application/json' -d '{"engaged": true, "reason": "test"}'`,
  then the page shows it engaged and the swarm button is refused.

### 8. The public demo

The same steps with `demo.tfvars` and `demo.backend.hcl` (`terraform init
-reconfigure -backend-config=demo.backend.hcl`). `demo.tfvars.example` starts
`place` with its kill switch engaged; release it through the API once the
smoke test passes and someone is watching the budget. Making the demo
public (linking it anywhere) waits for the launch gate in docs/PLAN.md
section 7.

Then take staging down (see [Tear down](#tear-down)) or shrink it, so the
two do not idle at $230 together.

## Operate it

- **Deploy a new version:** build and push new tags (step 4), set them in
  the environment's `.tfvars`, plan and apply. Aspen rolls over with no
  downtime. `place` stops its old task (last merge, then exit) before the
  new one starts, so the page is down for about a minute; that is the price
  of never running two merger bots at once.
  The live demo's `demo.tfvars` and `demo.backend.hcl` are kept by the
  maintainers, outside the repository. They keep `place_kill_switch = true`, so
  every deploy starts `place` with the kill switch engaged: release it with
  the operator token (`{"engaged": false}` to `/api/v1/admin/kill-switch`)
  once the new task is up.
- **Mirror the canvas to GitHub.** Set `place_canvas_mirror = "owner/name"`
  (an existing, empty repository) and apply. Put a credential with write
  access to that repository only into the secret the
  `place_canvas_mirror_key` output names: an ed25519 deploy key's private
  half (OpenSSH format; its public half added to the repository as a deploy
  key with write access), or, where the organization disables deploy keys,
  a fine-grained token with Contents read/write on that repository alone.
  `aws secretsmanager put-secret-value --secret-id <arn> --secret-string file://cred`,
  delete the local copy, and force a new deployment of the place service.
  The `canvas-mirror` sidecar fetches `main` from aspen-place at start and
  every `place_canvas_mirror_interval_seconds` (900) and pushes it when it
  moved, forced, so the mirror follows `main` when place starts its
  history again (`PLACE_HISTORY_MAX_BYTES`, or
  `/api/v1/admin/reset-history`); its
  log stream (`canvas-mirror/...` in the place log group) says when a push
  fails.
- **Stop the demo** without tearing it down: engage the kill switch (API),
  or set `place_running = false` and apply, which stops the task.
- **When a budget alert fires:** look at Cost Explorer by service first.
  - CloudFront: set `enable_cdn = false` in the environment's `.tfvars` and
    apply. That removes the distribution, so CloudFront stops serving and
    billing; Aspen keeps serving packs from `git.<base>/-/express` (traffic
    out of the ALB, which the account budget still watches). The kill
    switch and `place_running = false` do not stop CloudFront: the CDN
    serves Aspen's packs, not `place`. To find the cause, read the CDN's
    standard logs (bucket in the `cdn_log_bucket` output, kept 7 days):
    cache hits never reach the tasks, so the tasks' logs miss most CDN
    traffic. The CloudFront console's popular-objects and top-referrers
    reports give the same picture without downloading logs.
  - Data transfer out of the ALB: look for one client cloning in a loop
    (`aws logs tail /aspen/aspen-demo --since 1h` shows each request's
    path and status), and revoke its token.
  - Fargate or RDS: something was resized; compare with the `.tfvars`.
- **Logs:** `aws logs tail /aspen/aspen-<env> --follow` (Aspen, JSON lines)
  and `/aspen/aspen-<env>/place`.
- **Rotate the express key:** bump `express_keys_version`, apply, force a
  new deployment of the Aspen service. Fetches in flight for the next ten
  minutes may fail once and be retried.
- **Rotate the SSH host key:** bump `ssh_host_key_version`, apply, force a
  new deployment, publish the new `known_hosts` line. Every SSH client must
  update it.
- **Rotate the database passwords:** bump `db_password_version` (the RDS
  master user, which Aspen uses) or `place_db_password_version` (the
  `place` role), apply, then force a new deployment of the place service,
  and of the Aspen service for the master password. `place` gets the new
  password from its init container, which sets it on every start.
- **Database roles:** Aspen connects as the RDS master user to its database
  `aspen`. `place` connects as its own role `place`, which owns the
  database `place` and nothing else, and cannot connect to `aspen`: the
  task's `create-database` init container sets this up on every start
  (`environment/create-database.sh`, tested against PostgreSQL in CI). Only
  that init container gets the master password. `place` can still open the
  instance's default `postgres` database, which holds nothing.

## Tear down

```bash
# in staging.tfvars: db_deletion_protection = false, bucket_force_destroy = true
terraform apply -var-file=staging.tfvars
terraform destroy -var-file=staging.tfvars
```

RDS keeps a final snapshot (`aspen-<env>-final`); delete it when you no
longer need it. The account stack stays: its budget keeps watching.

## Known limits

- **A crash of `place` loses unmerged pushes from `main`.** Pushes accepted
  but not merged when the task dies stay on their branches; a SIGTERM merges
  first, a crash or OOM does not
  (#55). That is also
  why `place` never runs on Fargate Spot. A push still running when the
  20-second drain ends may finish during that last merge and then stays on
  its branch the same way.
- **SSH is off in the demo by default.** The per-address connection and
  failed-authentication limits exist (D4,
  #115;
  [docs/SSH.md](../../../../docs/SSH.md#what-happens-on-a-connection)), and
  the NLB passes each client's own address to them
  (#120). SSH stays
  off because the demo needs only HTTPS and the NLB costs about $24/month;
  whether staging, and then the demo, turn on `enable_ssh` is
  #195.
- **CDN URLs go to git 2.56 and later only**, because CloudFront answers
  `416` past the end of a cached object; older clients download from
  `git.<base>/-/express` instead (docs/EXPRESS.md).
- **Metrics are not scraped.** `/-/metrics` stays on the tasks' private
  listener; there is no Prometheus in this deployment yet.
- **One region**, and one `place` instance.

## Checks without an AWS account

From `deploy/terraform`:

```bash
(cd aws/public-demo/account && terraform init -backend=false && terraform test)
(cd aws/public-demo/environment && terraform init -backend=false && terraform test)
(cd aws && cp examples/isolated/.terraform.lock.hcl . && terraform init -backend=false && terraform test)
node aws/cdn/viewer-request.test.mjs
node aws/public-demo/environment/tests/place-live-viewer-request.test.mjs
(cd .. && deploy/scripts/check-terraform-write-only.sh)
PG_BIN=/usr/lib/postgresql/17/bin sh aws/public-demo/environment/tests/create-database.test.sh
```

The tests plan and apply the roots against mocked providers: one monthly
budget at the approved $20,000 and a daily one at $650, with no cost
filters, a validation that refuses more, alerts to email and SNS and no
budget action; an environment refuses to plan unless that budget exists
with at most the approved ceiling and no filters; the demo's place task and
database at their public-share sizes and staging's at the small ones; place on its own database, role and
bucket, as exactly one instance, never on Spot, behind the ALB by host,
and never with the RDS master password; no credentials in plain
environment variables; the CDN in front of `/-/express` with a path-only
cache key, its logs in a short-lived bucket, and the viewer function that
refuses expired URLs and paths that could be normalized. The write-only
check fails if a generated secret could enter Terraform state, and the
create-database test runs the init container's script against a local
PostgreSQL whose master user, like RDS's, is not a superuser.
`smoke.sh` runs against `aspen dev` and `aspen-place serve` on your
machine too (`ASPEN_URL=http://127.0.0.1:7070 SMOKE_REPO=demo
PLACE_URL=http://127.0.0.1:7080`); the CDN checks need a real
distribution.
